**2. DETECTION OVERVIEW**

**Description:**

This detection will detect the events of failed Azure AD “Consent to application” events where the consent context indicates admin consent (`ConsentContext.IsAdminConsent`) targeting a **Service Principal. **These failures can indicate a suspicious or unauthorised attempts to grant high-impact Oauth permissions (or probing), misused admin paths, or attacker experimentation consistent with OAuth/consent abuse patterns. We are aligning this activity with what had been observed in the engagement, and is built from **Real World Artefacts. **

**Hypothesis:**

my hypothesis is that an adversary will attempt to establish or expand access in a SaaS/Entra environment and may attempt to perform **consent-granting activity** for an application/service principal as part of cloud application persistence workflows. this is in line with **Cloud Application Integration (T1671).**

**MITRE ATT&CK® Mapping:**

- **Tactic(s):** Persistence (TA0003)
- **Technique(s):** **Cloud Application Integration (T1671)**

### **4. LOGIC & IMPLEMENTATION**

**Detection Logic (Pseudocode or SIEM Query):**

-- Provide the query here.  
-- Comment heavily to explain each logical step of the query.

```
rule soc_AzureAD_Consent_Security_Failure {
  meta:
    author = "Lucian Peckham"
    description = "Detects failed Azure AD 'Consent to application' events where admin consent context is present, targeting a Service Principal. Built from engagement activity artifacts to understand failed consent attempts and associated actor context."
    severity = "High"

  events:
    // 1) Primary data source + core event type
    $consent.metadata.log_type = "AZURE_AD_AUDIT"
    $consent.metadata.product_event_type = "Consent to application"

    // 2) Primary behavioral indicators (admin-consent path + SP target)
    $consent.target.resource.resource_type = "SERVICE_ACCOUNT"
    $consent.target.resource.resource_subtype = "ServicePrincipal"
    $consent.target.resource.attribute.labels.key = "ConsentContext.IsAdminConsent"

    // 3) Outcome filter to focus this analytic on failure events
    $consent.security_result.summary = "failure"

    // 4) Actor and key context extractions (used for triage + enrichment)
    $actor = $consent.principal.user.email_addresses
    $consent.principal.user.userid = $consent_user_id
    $consent.principal.user.user_display_name = $consent_user_upn
    $consent.principal.application = $consent_app_sp_id
    $consent.principal.ip = $consent_ip

    // Target naming (note: field choice depends on parser normalization)
    $consent.principal.resource.volume.name  = $target_sp_name

  outcome:
    // Single-event rule: still capture first observed time and assign risk score.
    $first_consent_time = min($consent.metadata.event_timestamp.seconds)
    $risk_score = 70

  condition:
    $consent
}
```

**Triage & Investigation Steps (Manual Playbook):**

\[Provide a clear, step-by-step checklist for the responding analyst.\]

1. **Initial Triage (Is this a true positive?):**
    1. Identify the actor: `actor email / user_id / display_name`
    2. Confirm source context: `principal.ip` (is it expected corporate/admin egress or unusual?)
    3. Confirm target: `service principal name / id` (what app/service principal was consent attempted for?)
    4. Confirm reason for failure (if available in normalized fields / description): look for authorization/policy failures

   **Investigation (What is the context?):**
    1. Look for adjacent events from the same actor/IP within 30–60 minutes then scope to an additional 1-5 timeframe:
        - Additional consent attempts (success/failure)
        - Investigate similar actions taken by threat actor utilising the line $consent.metadata.product\_event\_type:
            - Update service principal
            - Update application
            - Validate user authentication
            - Group dynamic properties retrieval
            - Certificates and secrets management (both update and creation)
            - Consent to application
            - Bulk job operations (creation, deletion, completion)
            - Application ownership and service principal modifications
        - App registration or service principal modification events
    2. Determine whether the target app is known/approved:
        - Is it a sanctioned integration?
        - Is it newly introduced?
        - is there previously observed activity that signifies this is normal behaviour? 
    3. Assess blast radius:
        - Was any consent eventually successful (companion “success” analytic recommended) run a query looking at that specific user and observed activity where the request was later approved
    4. If the activity aligns to suspicious behaviour, pivot into:
        - User risk signals
        - Recent sign-ins and anomalies
        - Any matching phishing indicators (separate workflow/alert family)

   **Response & Remediation (if suspicious/malicious):**
    - Confirm whether the account is compromised; initiate containment per SOC procedure
    - Block/disable the suspicious app integration path (app consent restrictions / tenant controls)
    - Review/cleanup OAuth grants and service principals if any success events occurred
    - Rotate credentials / review privileged access where relevant
