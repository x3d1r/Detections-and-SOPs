# 2. DETECTION OVERVIEW

## Description

Detects failed application consent events in Microsoft Azure Active Directory, now Microsoft Entra ID.

The detection identifies Azure AD audit events where an application consent operation targets a service principal, occurs within an administrative consent context and returns a failure result.

The rule was developed using behavioural artifacts observed during engagement-related activity. Monitoring failed consent attempts provides visibility into users, applications or automated processes attempting to grant access to an application, even where the consent operation does not complete successfully.

A failed consent operation does not confirm malicious activity. However, it may indicate:

- An attempted unauthorised administrative consent.
- A user attempting to approve a suspicious application.
- A compromised account attempting to grant application permissions.
- An application requesting permissions that cannot be granted.
- A consent attempt blocked by tenant policy.
- An incorrectly configured or unauthorised application.
- Reconnaissance or repeated testing of application consent controls.

## Hypothesis

We hypothesize that an adversary who has compromised an Azure AD account may attempt to grant consent to a malicious or adversary-controlled application.

If the account does not have the required privileges, tenant consent controls block the request or the operation is otherwise unsuccessful, the attempted action may appear as a failed application consent event in Azure AD audit logs.

This activity can be observed where:

- The log type is `AZURE_AD_AUDIT`.
- The product event type is `Consent to application`.
- The target resource is a service principal.
- The event contains an administrative consent context.
- The security result is recorded as `failure`.
- The event contains an identifiable user, application or source IP address.

**Selected Level:** Level 3, Core to Pre-Existing Tool

### Justification

The detection is based on Azure AD audit events generated by the Microsoft Entra application consent process.

The rule does not depend on a particular attacker-controlled tool, script, process name or command line. The consent request may be initiated through a browser, an OAuth authorisation flow, Microsoft Graph, PowerShell or another application interface.

The underlying audit behaviour is generated by a pre-existing cloud identity platform. However, the rule relies on specific normalised field values, including:

- `Consent to application`

# 4. LOGIC AND IMPLEMENTATION

## Detection Logic


rule soc\_AzureAD\_Consent\_Security\_Failure {

 meta:

 author = "Lucian Peckham"

 description = "Detects failed Azure AD application consent events targeting a service principal within an administrative consent context"

 severity = "High"

 events:

 $consent.metadata.log\_type = "AZURE\_AD\_AUDIT"

 $consent.metadata.product\_event\_type = "Consent to application"

 $consent.target.resource.resource\_type = "SERVICE\_ACCOUNT"

 $consent.target.resource.resource\_subtype = "ServicePrincipal"

 $consent.target.resource.attribute.labels.key = "ConsentContext.IsAdminConsent"

 $consent.security\_result.summary = "failure"

 $actor = $consent.principal.user.email\_addresses

 $consent.principal.user.userid = $consent\_user\_id

 $consent.principal.user.user\_display\_name = $consent\_user\_upn

 $consent.principal.application = $consent\_app\_sp\_id

 $consent.principal.ip = $consent\_ip

 $consent.principal.resource.volume.name = $target\_sp\_name

 outcome:

 $first\_consent\_time = min(

 $consent.metadata.event\_timestamp.seconds

 )

 $risk\_score = 70

 condition:

 $consent

}


## Plain-Language Logic


IF the event is an Azure AD audit event

AND the event type is "Consent to application"

AND the target resource is a service principal

AND the event contains the "ConsentContext.IsAdminConsent" label key

AND the security result is "failure"

THEN generate a high-severity detection

AND return the available actor, user, application, source IP and service principal context.


## Known False Positives

Potential legitimate triggers include:

- An administrator attempting to approve a legitimate application without sufficient permissions.
- A user attempting to consent to an application that requires administrative approval.
- A consent request blocked by tenant consent policy.
- A consent request blocked because the requested permissions are not permitted.
- A legitimate application with an incorrectly configured consent flow.
- An application requesting permissions that are not configured correctly.
- A test or development application using an invalid consent configuration.
- An expired or invalid application registration.
- An administrator testing application consent controls.
- An approved security test or adversary simulation.
- An automation process attempting to consent to an application using an identity without the required privileges.
- A service principal or application that has been deleted, disabled or incorrectly referenced.
- Repeated retries from a legitimate application after an initial configuration failure.

## Exclusion Strategy

Exclusions should be narrowly scoped and only introduced after the event has been investigated and the legitimate cause is understood.

Where available, exclusions should use a combination of:

- Known application ID.
- Known service principal ID.
- Expected initiating user or service identity.
- Approved application name.
- Expected tenant ID.
- Known source IP range.
- Expected consent operation.
- Change or service request reference.
- Approved testing window.
- Known automation context.

Avoid exclusions based solely on:

- Application display name.
- User display name.
- A broad source IP range.
- The event result being a failure.
- A single administrator account.
- Partial application name matching.

An application should only be excluded when:

1. The application owner is known.
2. The business purpose is documented.
3. The requested permissions have been reviewed.
4. The failed consent behaviour is understood.
5. The application ID and service principal ID have been validated.
6. The exclusion has documented approval.
7. The exclusion has a defined owner and review date.
8. Alternative monitoring remains in place for changes to the application.

Repeated failed consent attempts should not be excluded only because the application is legitimate. Repeated failures may indicate misconfiguration, unauthorised use or attempted abuse of the application.

## Implementation Notes

### Administrative Consent Label Validation

The current condition tests whether the following label key exists:


$consent.target.resource.attribute.labels.key = "ConsentContext.IsAdminConsent"


This confirms the presence of the label key but may not confirm whether the label value is `true`.

Before production deployment, inspect representative UDM events and confirm:

- Which field stores the label key.
- Which field stores the corresponding value.
- Whether the label value is represented as `true`, `True`, `1` or another value.
- Whether the label is always present for administrative consent operations.
- Whether failed non-administrative consent events contain the same key.

If both the key and value are available, the detection should verify the value rather than only checking that the key exists.

### Actor Variable

The rule assigns:


$actor = $consent.principal.user.email\_addresses


The `$actor` variable is not currently included in the outcome section or used as a match variable.

If the actor email address is required for case enrichment, it should be added to the outcome:


$actor\_email = array\_distinct($actor)


### User Variable Naming

The following condition assigns the principal user ID to `$consent_user_id`:


$consent.principal.user.userid = $consent\_user\_id


The following condition assigns the user display name to `$consent_user_upn`:


$consent.principal.user.user\_display\_name = $consent\_user\_upn


The variable name `$consent_user_upn` may be misleading because the source field is `user_display_name`, not a confirmed UPN field.

Consider renaming it to:


$consent\_user\_display\_name


If the UPN is required, validate whether it is present in:

- `principal.user.userid`
- `principal.user.email_addresses`
- Another normalised user field

### Principal Application Mapping

The rule uses:


$consent.principal.application = $consent\_app\_sp\_id


Confirm whether `principal.application` contains:

- An application name.
- An application ID.
- A service principal ID.
- A structured application object.
- Another normalised value.

The variable `$consent_app_sp_id` should only be used if the source field is confirmed to contain the service principal ID.

### Target Service Principal Name

The rule uses:


$consent.principal.resource.volume.name = $target\_sp\_name


This path appears under the principal resource rather than the target resource. Validate that this field contains the target service principal name.

If the service principal name is available under a target field, that target field should be used to avoid incorrectly attributing the principal resource as the consent target.

### Required Field Behaviour

The following assignments act as required conditions:


$consent.principal.user.userid = $consent\_user\_id

$consent.principal.user.user\_display\_name = $consent\_user\_upn

$consent.principal.application = $consent\_app\_sp\_id

$consent.principal.ip = $consent\_ip

$consent.principal.resource.volume.name = $target\_sp\_name


If any of these fields are absent from a valid failed consent event, the event may not match the rule.

Before production deployment, confirm whether all fields are consistently populated. Fields used only for enrichment should not unnecessarily prevent detection coverage.

### Rule Scope

The current rule detects single failed consent events. It does not currently correlate the consent failure with:

- Successful consent activity.
- Service principal credential changes.
- Certificate additions.
- Secret additions.
- Application role assignments.
- OAuth permission grants.
- Repeated consent attempts.
- Sign-in activity.
- Privilege changes.
- Subsequent application authentication.

The commented rule content indicates a potential future correlation between application consent and credential management activity. That correlation should be implemented and tested as a separate multi-event rule to keep the intent and response workflow clear.

## Triage and Investigation Steps

### Initial Triage: Is This a True Positive?

1. Identify the user or application that initiated the consent operation.
2. Confirm the event type is `Consent to application`.
3. Confirm the consent operation failed.
4. Identify the target application and service principal.
5. Determine whether the operation was an administrative consent attempt.
6. Identify the permissions or scopes requested by the application.
7. Review the source IP address.
8. Determine whether the initiating identity normally performs application administration.
9. Check whether the application is approved or known within the organisation.
10. Check for an associated change, service request, development activity or security test.
11. Determine whether the attempt was an isolated failure or part of repeated activity.
12. Confirm whether the same application later received successful consent.

### Investigation: What Is the Context?

1. Review the complete Azure AD audit event.
2. Identify the application ID.
3. Identify the service principal object ID.
4. Identify the application display name.
5. Identify the application owner or responsible business team.
6. Review the requested delegated and application permissions.
7. Determine whether any requested permission provides access to sensitive data or administrative functions.
8. Review recent sign-in activity for the initiating user.
9. Validate the source IP, location, device, user agent and application context.
10. Review MFA and Conditional Access results associated with the user’s recent sign-ins.
11. Determine whether the user recently received an administrative role.
12. Search for additional failed or successful consent events involving the same user.
13. Search for additional consent events involving the same application or service principal.
14. Check whether credentials, secrets or certificates were added to the service principal.
15. Check whether OAuth permission grants or application role assignments were created.
16. Check whether the application was recently registered, modified or granted a new owner.
17. Check whether the service principal was recently created or modified.
18. Review activity immediately before and after the consent attempt.
19. Determine whether the application authenticated successfully after the consent event.
20. Contact the initiating user and application owner through an independently verified channel.
21. Preserve relevant Azure AD audit, sign-in and application configuration evidence.

## Response and Remediation

### If the Activity Is Authorised

1. Document the legitimate application and business purpose.
2. Record the initiating user and application owner.
3. Record the requested permissions.
4. Link the relevant change or service request.
5. Confirm why the consent operation failed.
6. Assign configuration remediation to the application owner where required.
7. Close the alert with supporting evidence.
8. Only consider an exclusion if the failure is recurring, understood and formally approved.

### If the Activity Is Suspicious or Unauthorised

1. Escalate the event according to the cloud identity compromise process.
2. Block or disable the suspicious application or service principal where approved.
3. Revoke any permissions or consent subsequently granted to the application.
4. Remove unauthorised OAuth permission grants.
5. Remove unauthorised application role assignments.
6. Remove unknown application owners.
7. Remove unauthorised service principal credentials, certificates or secrets.
8. Revoke active user sessions and refresh tokens where account compromise is suspected.
9. Disable or temporarily block the initiating user where approved.
10. Reset the user’s credentials.
11. Require secure re-registration of authentication methods where appropriate.
12. Review all applications consented to by the affected user.
13. Review all activity associated with the application and service principal.
14. Identify any mail, file, directory or cloud resource access performed by the application.
15. Preserve Azure AD audit, sign-in and application configuration evidence.
16. Expand the investigation to determine the initial access method and total impact.

# ANALYST QUICK SUMMARY

## What Was Detected?

A failed Azure AD administrative application consent event targeting a service principal.

## Why Does It Matter?

An adversary with access to a cloud account may attempt to grant permissions to a malicious application. Even though the consent operation failed, the event may identify an attempted persistence or privilege escalation action before it succeeds.

## What Should I Do Next?

Identify the initiating user, target application, service principal and requested permissions.

Check whether the application is approved and whether the user was expected to perform the consent action. Review the user’s recent sign-ins and search for repeated consent attempts, successful consent, OAuth grants, role assignments, application changes, certificates or secrets associated with the same application.
