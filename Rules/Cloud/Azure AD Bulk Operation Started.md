# 2. DETECTION OVERVIEW

## Description

Detects the initiation of bulk operations in Microsoft Azure Active Directory, now Microsoft Entra ID, using Azure AD audit events.

Bulk identity operations can affect multiple users, groups or directory objects in a short period. Although these operations may be part of legitimate administration, they can also indicate that a compromised or misused privileged account is performing large-scale identity changes.

The rule reduces expected administrative noise by excluding approved service and administrative accounts maintained in the `soc_azure_ad_bulk_excluded_users` reference list.

## Hypothesis

We hypothesize that an adversary who has obtained access to a privileged Azure AD cloud account may initiate bulk directory operations to create, modify, delete or otherwise affect multiple identity objects.

This activity can be observed through Azure AD audit events where:

- The product event type indicates that an operation has started or is associated with a bulk operation.
- A principal user is identified.
- The principal user is not present in the approved bulk-operation exclusion list.

## MITRE ATT&CK Mapping

**Primary Mapping**

**Tactic(s):**

- Initial Access
- Persistence
- Privilege Escalation
- Defense Evasion

**Technique:** Valid Accounts

**Sub-technique:** Cloud Accounts, T1078.004

Valid cloud accounts may allow an adversary to perform actions across cloud environments, particularly when the compromised identity has elevated permissions.

**Potential Secondary Mappings**

The following mappings depend on the underlying bulk operation:

- Account Discovery: Cloud Account, T1087.004
- Permission Groups Discovery: Cloud Groups, T1069.003
- Create Account: Cloud Account, T1136.003

- Account Access Removal, T1531

These secondary mappings should only be applied when the underlying Azure AD audit activity confirms the specific action. The current rule detects that a bulk operation was started but does not determine exactly what the operation changed.

# 3. ANALYTIC DETAILS

## Analytic Robustness Level

**Selected Level:** Level 3, Core to Pre-Existing Tool

### Justification

The detection is based on audit events generated when Azure AD administrative functionality initiates an operation identified as started or bulk.

The rule is not dependent on a particular attacker-controlled executable, script name or command line. An adversary may use the Azure portal, Microsoft Graph, PowerShell, an administrative tool or another interface capable of triggering the same underlying Azure AD operation.

However, the current detection relies on the wording and classification of `metadata.product_event_type`. Changes to source normalisation or event naming could affect rule coverage. For this reason, the analytic is assessed as Level 3 rather than an invariant Level 5 behavioural detection.

- Level 1: Ephemeral
- Level 2: Core to Adversary-Brought Tool
- **Level 3: Core to Pre-Existing Tool**
- Level 4: Core to Some Implementations of a Sub-technique
- Level 5: Core to a Sub-technique, Invariant Behaviour

# 4. LOGIC AND IMPLEMENTATION

## Detection Logic


rule soc\_AzureAD\_bulk\_operation\_started {

 meta:

 author = "Lucian Peckham"

 description = "Detects when bulk operations are started in Azure AD, excluding known service/admin accounts"

 severity = "Medium"

 priority = "Medium"

 reference\_list\_name = "azure\_ad\_bulk\_excluded\_users"

 events:

 $event.metadata.log\_type = "AZURE\_AD\_AUDIT"

 $event.metadata.product\_event\_type = /started/

 or $event.metadata.product\_event\_type = /bulk/

 $event.principal.user.userid != ""

 not $event.principal.user.userid in %soc\_azure\_ad\_bulk\_excluded\_users

 outcome:

 $risk\_score = 35

 $event\_count = count\_distinct($[event.metadata.id](http://event.metadata.id))

 $principal\_user = array\_distinct($event.principal.user.userid)

 $target\_user = array\_distinct($event.target.user.userid)

 $src\_ip = array\_distinct($event.principal.ip)

 condition:

 $event

}


## Plain-Language Logic


IF the event is an Azure AD audit event

AND the product event type contains "started" or "bulk"

AND the principal user ID is populated

AND the principal user is not in the approved bulk-operation exclusion list

THEN generate a medium-severity detection

AND return the principal user, target users, source IP addresses and event count.


## Known False Positives

Potential legitimate triggers include:

- Approved bulk user onboarding or offboarding.
- HR-driven identity lifecycle operations.
- Bulk group membership changes.
- Planned tenant administration.
- Identity governance or access review processes.
- Approved automation using a named user account.
- Administrative scripts performing bulk updates.
- Directory synchronisation or migration activity.
- Incident response activity involving widespread account changes.
- Newly introduced service accounts not yet added to the exclusion list.
- Events containing `started` that are not related to bulk identity operations.

## Exclusion Strategy

The rule uses the `soc_azure_ad_bulk_excluded_users` reference list to exclude approved service and administrative identities that routinely perform expected bulk operations.

An account should only be added to the reference list when:

1. The account owner and operational purpose are known.
2. Bulk activity is an expected function of the account.
3. The account is appropriately controlled and monitored.
4. The exclusion has documented approval.
5. The exclusion has a defined owner and review date.
6. The account’s historical activity has been reviewed for consistency.

Excluded accounts should continue to be monitored for:

- Unexpected source IP addresses.
- New geographic locations.
- Unusual sign-in properties.
- Privilege changes.
- Authentication anomalies.
- Activity outside expected operational patterns.

Exclusions should not be based solely on display names, partial usernames or other easily changed values.

## Implementation Notes

The current event condition is broad:


$event.metadata.product\_event\_type = /started/

or $event.metadata.product\_event\_type = /bulk/


Before production deployment, validate the actual values stored in `metadata.product_event_type`.

If unrelated events contain `started`, the rule may generate unnecessary noise.

Where the parser provides suitable fields, the production version should preferably match:

- Confirmed bulk-operation event names.
- Exact or bounded product event type values.
- The underlying Azure AD operation name.
- Operation category.
- Result status.
- Initiating application or service principal.
- Target resource type.

## Triage and Investigation Steps

### Initial Triage: Is This a True Positive?

1. Identify the principal user that initiated the operation.
2. Identify the specific Azure AD operation name and category.
3. Confirm whether the operation was actually a bulk identity operation.
4. Review the event result or status to determine whether the operation succeeded, failed or only started.
5. Identify all available target users, groups or directory objects.
6. Review the number of distinct audit events returned by the detection.
7. Confirm the source IP address and initiating application.
8. Determine whether the principal is a standard user, privileged administrator, service account or automation identity.
9. Check for an approved change, service request, automation job or identity lifecycle process.
10. Confirm whether the account should already be present in the approved exclusion list.

### Investigation: What Is the Context?

1. Review the complete Azure AD audit record.
2. Determine exactly what objects were created, changed, removed or queried.
3. Identify the scope of the activity, including the number and type of affected objects.
4. Review recent Azure AD sign-in activity for the principal.
5. Check whether the source IP is known and expected for the user or service.
6. Review the authentication method, MFA result, Conditional Access result, device details, user agent and initiating application.
7. Determine whether the account recently received additional privileges.
8. Search for other bulk or administrative actions performed by the same principal.
9. Review activity immediately before and after the detected event.
10. Check for related user creation, user deletion, password resets, group changes, role assignments, MFA changes, application consent or credential creation.
11. Contact the account owner or responsible administrative team through an independently verified channel.
12. Preserve the relevant audit and sign-in evidence.

## Response and Remediation

### If the Activity Is Authorised

1. Document the approved change or business process.
2. Record the owner and purpose of the activity.
3. Close the alert with supporting evidence.
4. Consider an exclusion only if the activity is recurring and formally approved.
5. Do not exclude the account solely to resolve a single alert.

### If the Activity Is Suspicious or Unauthorised

1. Escalate the incident according to the identity compromise process.
2. Revoke active sessions and refresh tokens for the affected principal.
3. Disable or temporarily block the initiating account where approved.
4. Reset credentials and require secure re-registration of authentication methods.
5. Remove unauthorised role assignments or credentials.
6. Review and reverse unauthorised changes.
7. Identify all affected users, groups, roles, applications and directory objects.
8. Review connected cloud services for follow-on activity.
9. Block confirmed malicious source infrastructure where appropriate.
10. Preserve Azure AD audit, sign-in and related investigation evidence.
11. Expand the investigation to determine the initial access method and total impact.

## Automated Triage Logic


IF the principal user is disabled

OR does not normally perform administrative activity

THEN increase severity to High

AND add "Unexpected initiating identity" to the case findings.



IF the source IP has a malicious reputation

THEN increase severity to High

AND add the threat intelligence result to the case.



IF the source IP, country, device or application is inconsistent with the user's recent sign-in activity

THEN increase severity to High

AND add "Anomalous source context" to the case findings.



IF the bulk operation is followed by role assignment, user deletion,

credential change, MFA modification or widespread group changes

THEN increase severity to High

AND escalate for immediate analyst review.



IF a privileged role is assigned

OR multiple users lose access

OR authentication controls are modified at scale

THEN increase severity to Critical

AND require containment approval.



IF the operation corresponds to an approved change

AND the source identity, source IP and operation scope match the approval

THEN retain or lower severity

AND add the approval evidence to the case.



IF the user is present in the approved exclusion reference list

BUT the source context or operation type is inconsistent with expected behaviour

THEN do not automatically close the case

AND escalate for analyst review.

# ANALYST QUICK SUMMARY

## What Was Detected?

A user not present in the approved exclusion list initiated an Azure AD operation whose event type contains `started` or `bulk`.

## Why Does It Matter?

A compromised privileged account could use bulk operations to create, modify, remove or enumerate multiple cloud identities or directory objects.

## What Should I Do Next?

Confirm the exact operation, affected objects, initiating identity, source IP address and sign-in context.

Check for an approved change, then investigate related role, group, account and authentication changes before considering containment.
