**2. DETECTION OVERVIEW**

**Description:**

This detection identifies Azure AD service principals that have first been updated and are subsequently observed having credentials added within a 48-hour period. The detection correlates both events against the same service principal resource name to identify potentially suspicious application persistence activity.

The creation of new credentials on an existing service principal can provide long-term access to cloud applications and services. When credential creation follows a modification to the service principal, it may indicate administrative changes immediately preceding the establishment of alternate authentication material. This activity is consistent with cloud account persistence techniques and may represent legitimate administration, application onboarding, automation development, or adversary attempts to maintain access.

This analytic was developed to identify service principal modification workflows that may otherwise appear benign when viewed as individual events.

**Hypothesis:**

My hypothesis is that an adversary who has obtained privileges within an Entra ID/Azure AD tenant may modify an existing service principal and subsequently add credentials to establish persistent application-level access. This activity would allow authentication to Azure resources without reliance on traditional user accounts and aligns with known cloud persistence techniques.

### **4. LOGIC & IMPLEMENTATION**

**Detection Logic (Pseudocode or SIEM Query):**

-- Provide the query here.  
-- Comment heavily to explain each logical step of the query.

```
rule soc_AzureAD_Update_Service_Principal_Credentials_Followed_by_Add_Service_Principal {

  meta:
    author = "Lucian Peckham"
    description = "Detects Azure AD service principal being updated and correlates on add service principal activity"
    severity = "Medium"

  events:

    re.regex($app.metadata.product_event_type, "Update service principal") nocase

    $app.target.resource.name = $Resource_Name


    // Restrict $owner to Azure AD Directory Audit logs as well
    // $owner.metadata.product_name = "Azure AD Directory Audit"

    // Restrict $owner vendor to Microsoft for consistency and source hygiene
    // $owner.metadata.vendor_name = "Microsoft"

    // (So we are correlating actions on the same named resource/object.)
    $owner.target.resource.name = $Resource_Name


    re.regex($owner.metadata.product_event_type, "Add service principal credentials") nocase 
    $owner.metadata.event_type = "USER_CHANGE_PASSWORD"

  match:

    $Resource_Name over 48h


  outcome:
    // Static risk score assigned when the rule matches
    $risk_score = 60
    // Count distinct anchor-event IDs involved in the match
    $event_count = count_distinct($app.metadata.id)
    // (Useful to spot unusual geography)
    $principal_county_region = array_distinct($app.principal.ip_geo_artifact.location.country_or_region)

    // Collect distinct follow-on (correlated) product event types observed in $owner
    $owner_event_type = array_distinct($owner.metadata.product_event_type)


    // Collect distinct anchor ($app) product event types observed (if populated by source)
    $app_event_type = array_distinct($app.metadata.product_event_type)

    $App_User_Name = array_distinct($app.principal.user.userid)

    $Owner_User_Name = array_distinct($owner.principal.user.userid)

    $app_User_Agent = array_distinct($app.network.http.user_agent)

  condition:
    // Fire only when BOTH the anchor event ($app) and correlated follow-on event ($owner) exist
    // within the correlation defined in match:
    $app and $owner
}
```

**Triage & Investigation Steps (Manual Playbook):**

\[Provide a clear, step-by-step checklist for the responding analyst.\]

1. **Initial Triage (Is this a true positive?):**
    1. Identify the actor: `actor email / user_id / display_name`
    2. Confirm source context: `principal.ip` (is it expected corporate/admin egress or unusual?)
    3. Confirm target: `service principal name / id` (what app/service principal was consent attempted for?)
    4. Confirm reason for failure (if available in normalized fields / description): look for authorization/policy failures

   **Investigation (What is the context?):**
    1. Look for adjacent events from the same actor/IP within 30–60 minutes then scope to an additional 1-5 timeframe:
        - Additional consent attempts (success/failure)
        - Investigate similar actions taken by threat actor utilising the line $consent.metadata.product\_event\_type:
            - Update service principal
            - Update application
            - Validate user authentication
            - Group dynamic properties retrieval
            - Certificates and secrets management (both update and creation)
            - Consent to application
            - Bulk job operations (creation, deletion, completion)
            - Application ownership and service principal modifications
        - App registration or service principal modification events
    2. Determine whether the target app is known/approved:
        - Is it a sanctioned integration?
        - Is it newly introduced?
        - is there previously observed activity that signifies this is normal behaviour? 
    3. Assess blast radius:
        - Was any consent eventually successful (companion “success” analytic recommended) run a query looking at that specific user and observed activity where the request was later approved
    4. If the activity aligns to suspicious behaviour, pivot into:
        - User risk signals
        - Recent sign-ins and anomalies
        - Any matching phishing indicators (separate workflow/alert family)

   **Response & Remediation (if suspicious/malicious):**
    - Confirm whether the account is compromised; initiate containment per SOC procedure
    - Block/disable the suspicious app integration path (app consent restrictions / tenant controls)
    - Review/cleanup OAuth grants and service principals if any success events occurred
    - Rotate credentials / review privileged access where relevant
